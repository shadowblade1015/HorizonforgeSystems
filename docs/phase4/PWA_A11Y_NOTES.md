# Phase 4 independent PWA and accessibility source review

Reviewed October 25, 2026. This workstream read the current worker, release generator, builder, verifier, offline client, app boot, UI modal/router, FX, board accessibility integration, game HTML, CSS, deployment configuration, original audit and Phase 3E/3F reports/matrices. Prior reports were context, not proof. No production source was changed and no browser was launched by this workstream. Browser evidence collected by the coordinating reviewer must be distinguished from the deterministic reproductions below.

## Confirmed findings

### PWA-01: optional-download completion can claim offline availability with missing core

- Severity: medium (P2). Conditional probability: certain after the reproduced sequence; real-world frequency depends on partial cache eviction. Impact is a misleading readiness statement and possible failed offline launch, not demonstrated save loss.
- Location: `site/ember-solitaire/js/offline.js:82-93`, particularly 87-90; `site/ember-solitaire/sw.js:160-168,178-181`.
- Sequence: complete core installation; keep the game document open; delete only the release cache's `js/engine.js` entry to model partial eviction; invoke Download all artwork while online; disconnect and request that missing engine entry.
- Current behavior: STATUS reports `ok:false`; DOWNLOAD processes only optional files and replies `{ok:true,failed:0}`; STATUS remains false. The client checks the release identity but ignores readiness, then tells the player "All suit modes, backs and tables are available offline." The missing engine request returns 503 offline.
- Reproduction executed: production worker template in the existing `tests/offline.test.mjs` VM adapters, with no change to production or test files. Observed status before/after false, download true/zero failures, missing engine offline status 503. A real-browser reproduction was requested from the coordinating reviewer; do not label this workstream's VM result as an OS eviction experiment.
- Owner: PWA client/worker maintainer. Minimal fix: require core readiness before giving the complete offline-play promise and recheck it after optional downloads; otherwise clearly say artwork downloaded but core repair is required. A network repair should remain player controlled and preserve cached good entries/save data. Add a regression covering this sequence.
- Effort: small, approximately half a day with targeted browser regression. Gate: resolve or explicitly accept before certifying the full offline-availability contract; it does not independently block an accurately described online-only release.

### A11Y-01: enabling OS reduced motion during a session leaves canvas particles running

- Severity: medium (P2 accessibility), conditional probability certain on an already running ambient field. No gameplay or save mutation was demonstrated.
- Location: `site/ember-solitaire/js/fx.js:6-7,42-70,86-96`. The media query is read when starting a field; the animation loop does not recheck it and there is no media-query change subscription.
- Sequence: run home/forge with reduced motion initially off; change the operating-system/browser media preference to reduce without navigating, hiding the document or toggling the game's setting.
- Reproduction executed: evaluate the actual FX source with a controllable MediaQueryList and animation-frame adapter; start `setField('home')`, run a frame, set `mq.matches=true`, run the next frame. Observed `motion()===false`, yet 34 additional drawImage calls, canvas opacity 1, and zero media-query change listeners. CSS media queries do update independently, so this is specifically the continuing JavaScript effect.
- Owner: accessibility/UI maintainer. Minimal fix: subscribe to preference changes, stop/clear the owned canvas loop and update parallax immediately; restore eligible effects only when motion becomes allowed. Defensively recheck motion inside the loop. Add deterministic preference-change coverage plus real browser emulated-media verification.
- Effort: small, approximately half a day. Gate: fix before claiming dynamic reduced-motion support or accessibility certification. Physical assistive-technology/device checks remain necessary afterward.

## Independently inspected protections and boundaries

- Release identity covers sorted exact game bytes plus the normalized generator implementation (`tools/release.mjs:7-10`). Generated HTML binds immutable release paths and script/style SHA-256 integrity (`12-18`). The dedicated worker's relative engine import stays in that release subtree. No dependency/framework addition was found in this mechanism.
- The worker validates fetched response status/type/redirect, byte length and SHA-256 before cache insertion (`sw.js:14-23`), with a ready marker written after complete core/catalog storage (`72-80`). Failed candidates remove only their candidate cache. GET/scope routing and explicit unknown-navigation 404 handling are present (`126-155`). Optional downloads acknowledge awaited writes rather than merely a successful fetch.
- Explicit update approval performs protected immediate saves and board holds; modern takeover verifies the expected ready controller before reload (`offline.js:43-79`). This workstream did not find a new path that clears player storage. The historical bridge intentionally reloads only an already loaded verified same-bundle release after protected saves; real lifecycle validation belongs to the same-origin browser suite.
- Cache retirement pins live identified clients, active and pending releases; unknown clients prevent deletion. Only names in the protocol-owned namespace with a valid release ID are retired (`sw.js:35-54`). Four retained releases is an intentional installation limit, not a promise of unbounded update history. Legacy caches are deliberately retained read-only. Multi-tab save coordination is still not implemented and must not be inferred from compatible bundles.
- Builder retains exclusive lock, fresh staging, validation before rename, backup retention and rollback on publication failure (`build.mjs:7-34`). Verification regenerates every expected byte and rejects missing/changed/stale output, preserving the hard-coded historical archive hash (`tools/verify-source.mjs:54-67`). This is strong current-output verification, not an independent proof of generator correctness.
- Modal ownership isolates background app children and coordinates top-modal Tab/Escape/focus restoration (`ui.js:15-62`); HTML supplies named native column/run controls and board instructions (`index.html:69-92`). CSS includes safe-area scrolling, minimum target sizing, modal scroll bounds and narrow container reflow. These are inspected implementations, not a claim that all WCAG criteria passed.

## Save-safe deployment and rollback gates

Keep the current Phase 3F protocol and matching source/generator/build tools together. Publish complete validated output atomically; never replace only HTML/worker files. A rollback to the historical pre-3F worker reintroduces automatic activation, old cleanup and unversioned release mixing; it is unsuitable as the production rollback strategy. Preserve existing saves, recovery copies and original archive/inventory. Never recommend clearing site data to repair offline storage.

Current-release cache repair needs connectivity and matching deployed assets. If an old pinned release is evicted after its host paths disappear, it deliberately fails closed. Export progress, close older tabs and reopen the ready current release; do not invent availability guarantees for permanently evicted old code. Deployment owner should verify historical immutable URL availability on the actual host and document that limit during release approval.

No live deployment/header inspection, physical device test, screen-reader session or app-store package certification was performed by this workstream. Refer to the coordinating Phase 4 report for the final command results, browser evidence and consolidated gate decision.

## Additional portfolio, artwork and audio review

`site/app.js:1-4` uses a responsive navigation disclosure and a native named project dialog; close restores its opener. Project `innerHTML` content is a fixed local catalog, not an observed remote input. `site/pages.js:4-16` validates contact fields, sets the preview with textContent, encodes mailto components, distinguishes preparing from sending, and offers a manual-copy fallback. Portfolio CSS (`site/style.css`, minified lines 2-9) contains responsive navigation/dialog rules and a dynamically effective reduced-motion override. Neither email delivery nor clipboard availability was externally certified. Missing Escape handling on the nonmodal navigation disclosure is an enhancement candidate, not evidence of a focus trap.

`js/icons.js:43-59` generates controlled decorative SVG paths; `js/artifacts.js:278-318` generates labeled artifact artwork and heat-mask state from the artifact catalog. Existing SVG fragment references should still receive browser rendering review under generated bases; source inspection alone does not prove composited gradients/masks or all artwork contrast. No new remote injection source was found for these templates. The artifact API's unrestricted custom label/class options should not later receive unescaped external text.

Audio has a native-integration risk candidate: `js/audio.js:95-101` resumes the context on foreground when music/SFX are enabled without checking the `suspended` full-screen-ad flag; `unlock()` at line 28 similarly resumes it. A hide/foreground cycle during an ongoing full-screen ad could resume the synth/music before ad dismissal. This is source-confirmed control flow, not a reproduced native AdMob failure; browser advertising is disabled. Native owner should gate visibility/unlock resume on the explicit suspension state and verify on a real native build if that product is proposed. This is not an independently established browser-web-launch blocker. Synth initialization/resume failure behavior and audio preference ergonomics also require real browser/device checks; no audio backend or dependency was added during the audit.
