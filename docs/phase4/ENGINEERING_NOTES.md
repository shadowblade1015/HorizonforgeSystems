# Independent engineering review

Phase 4 audit, 2026-10-25. Production code is unchanged. This is supporting evidence for the consolidated issue register, not a release approval.

## FAIL: F08 concurrent tab progress loss

**P1, web and PWA save-integrity gate.** Reproduced deterministically in three independent-context tests using the real Store module and a shared storage adapter. Probability is certain when a stale second tab writes after the first advances; frequency among real players is unknown. No account or malicious input is required.

Affected current source: `site/ember-solitaire/js/store.js:228-256` loads independent state; `:264-273` writes the context's `lastGoodRaw` to backup and then replaces the primary without comparing current storage; `:279-290` acknowledges success. `site/ember-solitaire/js/app.js:36-37` flushes on hidden/pagehide, so a stale tab need not make a deliberate game action.

Exact reproduction: create fresh storage; open A and B and load both; A earns 100 Ember and saves immediately; B changes music and saves immediately. Observed stored `totalEmber`: **100 -> 0**; backup is also **0**; B reports `saved`; no recovery entry retains A. A second case starts a valid two-suit hand in A and then immediately saves the stale handless B: both primary and backup lose the hand. A third case places a future-schema raw value into storage after A has loaded; A's next immediate save silently replaces that raw value with v2 and retains no original copy. Future-version protection is effective at initial load, not against already-running old tabs.

Evidence: `tests/phase4-audit.test.mjs`, first three cases. These are deliberately named **OBSERVED DEFECT** and pass by proving current loss. They are audit probes, not assertions that this behavior is acceptable. Change their expected outcome to preservation/refusal on a separate remediation branch.

Smallest safe remediation: adopt a single active writer using a cross-tab coordination primitive with an explicit unsupported-platform fallback; before replacement compare the exact loaded/saved storage revision or raw snapshot, retain the conflicting raw value, block stale writes and offer export/reload. A bare `storage` listener is useful notification but is not atomic write arbitration. Protect every writer including lifecycle flush, reset, recovery/import and upgrades; preserve earned currency and hand/reward receipts as one profile. Do not merge currency totals heuristically. Mitigation until fixed: a clearly visible single-tab restriction reduces risk but is not an enforced safety boundary; do not mark the defect fixed by a warning. Owner: persistence engineer. Estimate **2-4 engineering days plus 1-2 QA days**, assuming no cross-tab merging or cloud save. Separate remediation branch recommended before public web/PWA sign-off.

## FAIL: F13 synchronous solver blocking remains

**P2, performance/interaction gate.** Current source `site/ember-solitaire/js/board.js:464-472` directly invokes `solveEndgame(g,20000)` on the main thread after the endgame debounce. `:480-494` normally delegates stuck detection to a worker but executes `isStuck()` synchronously when worker creation or execution fails. `site/ember-solitaire/js/engine.js:266-293` uses recursive DFS and allocation of cloned positions/path arrays. A node-count budget does not limit elapsed time per frame; no wall-time cancellation or recursion-depth guard exists.

Independent reproducible fixture: `g=Engine.newGame(4,{seed:42})`; deal all five stock rows; mark all remaining cards face up; clear history; `Store.validateHand(g)` returns true; call `Engine.solveEndgame(g,20000)` and measure with `performance.now()`. First local desktop Node run took **669 ms** on seed42 (other sampled seeds 0-413 ms). These are constructed schema-valid stress states, not recorded reachable player traces. See ignored `.phase2-backup/phase4/solver-node.json` for repeated raw timings/runtime. Browser and throttled measurements belong in the consolidated performance report. Do not report Node timings as mobile latency or real-user INP.

Impact: visible unresponsiveness during qualifying all-up, stock-empty endgames, potentially magnified on low-end devices. Exact prevalence in normal play remains unmeasured. No stack overflow was reproduced in these samples; recursion overflow remains a suspected risk, not a confirmed finding. Smallest safe remediation: extend the existing worker with revision-tagged auto-complete requests, cancellation and a wall-time/budget-exhausted result; if worker is unavailable, suppress the optional suggestion rather than run a long synchronous fallback. Keep player actions available. Owner: engine/performance engineer. Estimate **1-3 engineering days plus 1 QA day**. Can be scheduled after a limited web trial if measured device performance and an explicit owner/mitigation are accepted; not a P1 by itself.

## Remaining heuristic and platform limitations

**F15, P2 source-confirmed heuristic limitation, not reproduced false-positive.** `engine.js:298-319` searches depth six and memoizes a position without remaining depth (`:306`). A deeper first visit can prune a later shallower path. The budget exhausts conservatively, but a bounded local-progress search cannot prove no winning path. `screens.js:178-199` offers Keep looking/Undo/restart, preserving agency, though its explanatory wording is stronger than the heuristic warrants. Smallest safe change: store greatest remaining depth per position and describe "No progress found in this search". Effort **0.5-1 engineering day plus fixture QA**; nonblocking with current dismissible UI. Construct a known false-positive fixture before claiming a corrected search result.

**Native persistence, Android-only gate:** `platform.js:29-41` hydrates Preferences into localStorage before Store validation/quarantine. The commercial/Android reviewer independently reproduced overwrite of a protected future local raw value. Use that review's retained probe and issue entry; this note does not duplicate its finding. `platform.js:23-25,43` catches optional plugin failures and does not expose a durable native acknowledgement; OS process termination, disk failure and asynchronous Preferences write ordering remain **NOT TESTED on devices**. Normal web builds do not enter this path.

**Daily integrity:** daily dates/seeds use the client clock (`store.js:29-32,528`; `screens.js:311-351`). There is no authoritative server date, leaderboard or paid-prize boundary. Daily awards are ledger guarded (`store.js:483-490`) and settlement remains hand-receipt guarded (`:467-517`). Clock tampering can manufacture dates in a local-only profile; this is an expected trust limitation, not a remote financial security vulnerability. Reassess before competitive/prize-bearing features. Native and production analytics/ad flows require separate SDK/publisher checks.

## PASS evidence and limits

The fourth independent audit test exercises **1/2/4 suits x four seeds x up to 60 legal actions**: enumerate legal moves, deal, undo, validate every position, immediately save, export, reload and compare exact persisted state. The persisted 20-history limit is asserted explicitly; the fixture explicitly selects its first artifact so documented legacy defaulting is not confused with mutation. All **4 audit tests pass**, including the three defect observations. This establishes sampled invariants, not exhaustive game solvability or browser interaction.

Source review found the save boundary uses canonical deck identity/rank/suit counts, face-up suffix consistency, complete columns/stock/history, supported v2 profile validation and protected quarantine. Settlement receipts live outside undo history and block repeat victory payout. Runtime board ownership checks tie work to game/session/revision/epoch, cancel workers/timers/animations on invalidation and keep modal/hidden/inactive games from accepting ordinary actions. These are supported by the existing rule, persistence, victory and lifecycle suites, which must be independently rerun by the release lead. No production invariant was relaxed for this audit.

Security review did not identify a reproduced remote code-execution or remotely exploitable save injection boundary in these modules. Saves are local user-controlled JSON, validated/cloned; profile map keys are constrained artifact/date identifiers. This is not a penetration-test certification, CSP/header verdict or validation of external native SDK behavior. Full deployment/header, service-worker, accessibility and commercial gates are covered by the other workstreams; no physical screen-reader/mobile/native tests are implied by this note.
