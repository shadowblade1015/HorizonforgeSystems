## Reproduced native boundary defect AND-01

**FAIL / P1; native save-integrity gate.** `platform.js:29-41` reads local and Preferences JSON, compares only savedAt and replaces localStorage before `app.js:10-11` calls the validated Store loader. It neither validates the candidate profile nor preserves the displaced raw copy first.

Reproduction runs the actual platform.js in an isolated Node VM with native true and a fake Preferences.get. A complete current Store export with 1 Ember and `savedAt:20` is independently accepted by Store.load. The local raw is a copy with `v:999`, `savedAt:10` and 900 Ember. Calling `Platform.hydrate('ember.save.v2')` replaces that unsupported future local raw with the newer-timestamp valid v2 candidate. `.phase2-backup/phase4/native-boundary-probe.json` records both complete raw values and `originalPreserved:false`. The overwritten raw cannot subsequently be quarantined by Store.load because it is already gone. An initial minimal schema-tag probe was strengthened to this complete validated-candidate reproduction. Probability is certain when these conditions occur; real-device frequency is unknown. Browser native=false path is unaffected.

Smallest proposed separate fix: preserve both raw candidates before choosing; validate schema and save completeness through the same Store boundary; never overwrite a future/unsupported candidate automatically; provide a visible recover/export choice for conflicts. Add regression cases for future-local/older-native, invalid-newer-native/valid-local, parse errors and writes failing. Owner: native/persistence engineer. Estimate: 2-4 engineer days plus device regression. Do not ship native progress migration with this behavior.

## Additional native risks

**AND-02 — Durability acknowledgment: NOT TESTED physical durability / P2 source-evidenced robustness risk.** `platform.js:23-25,43` swallows rejected plugin calls and persist does not return the Preferences promise; `store.js:276` treats local write success as saved without native acknowledgment. A save can appear saved although the durable native replica failed. Exact condition: Preferences.set rejects while localStorage succeeds, followed by WebView data eviction/process loss; the latter was not exercised on a device. Proposal: await and surface native-replica acknowledgment separately, retain local/raw backups, test delayed/rejected writes, background/process death and restore. Owner: native engineer; 1-3 days plus physical tests. Native launch gate, not a claim of current web data loss.

**AND-03 — Native Firebase consent: FAIL / P1.** See COM-02 in MONETIZATION_REVIEW.md and the deterministic probe: analytics.js:23-25,38-42 enables a native Firebase event before any consent application; app.js:28-31 invokes remote config/custom keys before UMP completion. Production plugin defaults, automatic collection and real network behavior remain NOT TESTED. A privacy-safe SDK initialization/choice implementation and native capture are required. Owner: native/privacy; 2-5 days.

## Current official requirements and package plan

The [current Google Play target API requirements](https://support.google.com/googleplay/android-developer/answer/11926878), checked October 25, 2026, require new ordinary phone/tablet apps and updates to target **Android 16 / API 36 or higher from August 31, 2026**. Do not use the older API 35 submission threshold. No target SDK has been verified here. Reconfirm policy and any account-specific exceptions when a package is prepared.

[Android signing guidance](https://developer.android.com/studio/publish/app-signing) requires a signed bundle/upload key and Play App Signing workflow. The release owner must retain control of signing identity and rollback/update strategy; do not store signing secrets in this repository. [Play Data Safety guidance](https://support.google.com/googleplay/android-developer/answer/10787469) includes third-party SDK data handling. A local-only game does not justify declaring no data collection once ads/analytics/crash SDKs are added. [UMP integration guidance](https://developers.google.com/admob/android/privacy) requires correct native dependencies/manifest and launch-time consent updates. [Play testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465) depend on developer-account eligibility; verify applicable closed-test/production-access obligations in the actual account instead of assuming they are satisfied.

Future engineering must establish a pinned reproducible Capacitor/native project, package ID, target/min SDK, bundled asset routing and release-base compatibility. The web generator emits absolute `/ember-solitaire/_releases/...` URLs; test their resolution in the selected local WebView server rather than blindly copying dist to a different www root. `offline.js:107` excludes Capacitor from browser service-worker registration, so native offline availability depends on packaged assets and native hosting, not the PWA cache tests.

Use internal test units and test devices; verify UMP geography/withdrawal, SDK versions and any native-library page-size compatibility before production. Run packaged tests for cold start, offline play, one/two/four suits, accessibility/TalkBack, back navigation, rotation/tablets, foreground/background clocks, audio, reward callbacks, activity recreation, low memory, kill/relaunch, rejected storage writes, WebView cache/data eviction, backup/restore and upgrade save migration. Confirm no reward is granted from a show-call success without the SDK's actual reward signal (`ads.js:105-112` requires plugin-specific verification; no real plugin was available). Store screenshots must come from the final package. Publisher/legal review owns disclosures, target audience, permissions, ad-content settings, listing and account approval.

Rough planning estimate: **10-25 engineer days plus 3-8 QA/device days**, assuming current web behavior is stable, an existing verified Play developer account and no major plugin compatibility issue. External review, developer verification, closed-test elapsed time, policy decisions and signing recovery are additional dependencies. This estimate is not a release promise. Keep Android on a separate remediation/packaging branch; no native output or production changes belong in this audit pass.
